1. Data & backend: small but crucial schema tweaks

You already have most of the pieces (users, profiles, health_profiles, consents, consent_events, guardian_verifications, xids, programs, program_events, attendance).

Add 3 small but powerful tables:

1.1. guardian_links

To link youth ↔ parent:

id

youth_user_id (FK → users)

guardian_user_id (FK → users)

relationship (e.g. parent, aunt, caregiver)

primary_contact (bool)

created_at

Use:
Once a guardian completes verification, create a guardian user and a guardian_links row. This is the backbone for the parent portal and program consent routing.

1.2. program_consent_requests

Per-program consent state:

id

youth_user_id

guardian_user_id

program_id (and optionally program_event_id)

status → 'pending' | 'approved' | 'declined' | 'revoked'

requested_scopes (text[]: e.g. ['contact','emergency','health'])

created_at

responded_at

Use:
Whenever a youth RSVPs / checks into a program that requires consent, create or reuse a row here. This is your “Sign in with Room XI for consent” primitive.

1.3. Separate demographics: youth_demographics + guardian_demographics

To respect youth privacy (e.g. not outing queer youth) and make your research powerful:

A. youth_demographics

user_id (PK)

gender_identity

sexual_orientation

race_ethnicity

language_at_home

disability_status

other self-view fields

Private to youth + aggregate analytics. Parents never see this.

B. guardian_demographics

youth_user_id (PK)

guardian_user_id

perceived_gender_identity

perceived_race_ethnicity

household_income_band

household_structure

etc.

Visible in parent portal, not in youth app.
Org/funder reporting uses this + anonymized youth data, aligned with the coordinated intake and outcome tracking model in your research.

2. Youth signup → parent email → platform consent

This is your “consent to be on the app at all”.

You already have:

Multi-step youth signup UI (Signup.tsx)

Guardian verification endpoints (/consent/guardian/*)

guardian_verifications table and services

Now we formalize the flow.

2.1. Signup changes

In Signup.tsx:

Require guardian contact for youth under your chosen age threshold (e.g. under 16):

guardianContactType: 'email' | 'sms'

guardianContactValue

On successful signup (after creating the youth user and profile):

await api.consent.requestGuardianVerification(
  formData.guardianContactType,
  formData.guardianContactValue
);


Then show a “We’ve emailed your parent/guardian” screen:

Youth can still:

Browse programs

Use mood check-ins

Talk to Ximi

But clearly mark some features as “pending guardian consent” if needed.

This matches your research’s emphasis on coordinated intake with proper consent, especially for minors.

2.2. Guardian verification → platform consent

In /consent/guardian/verify/:token:

On successful verification:

If guardian user doesn’t exist:

Create a guardian users row (with their email).

Create a guardian_links row.

Insert a consents entry:

consent_type = 'platform_app_use'

value = true

granted_by = 'guardian'

Insert a consent_events row:

actor = 'guardian'

event_type = 'granted'

consent_key = 'platform_app_use'

Now you can safely say:

“This youth has guardian consent to use Room XI and to store their intake data.”

That’s your baseline consent, required by Alberta privacy expectations (PIPA/FOIP) in the research.

3. Program consent: “Sign in with Room XI” for youth programs

You want Room XI to become the standard consent broker between youth and programs. Think of it like:

“Instead of ‘Sign in with Google’, orgs ‘Request consent via Room XI’.”

For MVP, just support in-app programs and your own org partners; later you can open it as an API.

3.1. Program metadata

In programs table add (if not already):

requires_guardian_consent boolean

requires_registration boolean

requested_scopes text[]
(e.g. ['contact','emergency','health'])

Org admins set these in OrgDashboard.

3.2. Youth RSVP / check-in triggers consent request

In RSVP endpoint and xid/attendance handler:

When a youth RSVPs or scans into a program:

Check program.requires_guardian_consent.

If true, find primary guardian via guardian_links.

Check for existing program_consent_requests for (youth, program).

If none (or revoked/declined):

Create program_consent_requests row with status = 'pending'.

Send guardian email/push:

“[Youth name] wants to participate in [Program]. They’re asking to share intake info: [scopes]. Review and consent here.”

Youth can still have their attendance recorded (depending on your policy), but the org only sees full intake after approval.

This fits perfectly with the “coordinated intake + warm referrals + no-wrong-door” approach in your research, while being practical.

4. Lightweight one-page parent portal

You asked for: one page with everything but done properly.

Make a single route, e.g. /guardian/portal, with 3 stacked sections:

4.1. Section A – Linked youth & basic safety

Cards for each youth:

Name / preferred name

Age

Quick safety banner: “Emergency contacts complete” / “Missing emergency contact info”

Button to “Update intake & safety info”.

Behind the scenes:

Reads from profiles, health_profiles, and guardian_demographics.

Does NOT show youth’s private demographics (youth_demographics).

4.2. Section B – Consent center

For each youth:

Program consent requests (from program_consent_requests):

Status badges: Pending / Approved / Revoked.

For Pending:

Program name, org, short description.

Icons or chips showing requested scopes (contact, emergency, health, etc.).

Buttons: Approve, Decline.

Approve flow:

Backend:

Update status = 'approved'.

responded_at = now().

Log in consent_events with consent_key = 'program:<id>'.

Revoke button:

Change status to 'revoked'.

Log consent_events with event_type = 'revoked'.

This gives parents a clear, simple “inbox” of consents, just like they’d see approvals in Google / Apple.

4.3. Section C – Activity & mood overview

For each youth:

Basic attendance timeline:

Last X check-ins with program names and dates.

Simple mood trend summary:

“Most common feelings this month: 😌 calm, 🙂 okay”

Very high level, not detailed journal content.

No raw check-in notes, no sensitive text — just aggregated mood and attendance.

This mirrors the research’s idea of parents seeing high-level updates without violating youth privacy.

This delivers what your research calls “youth-centered engagement & wellbeing check-ins” but in a minimal, non-intrusive way for MVP.

6. Ximi floating AI: keep it, but constrain the role

You want Ximi to stay as you originally intended, with role/purpose/attachment, and the research backs that (AI navigation, coaching, etc.).

For MVP, keep Ximi focused and safe:

Primary skills:

Program navigator

“I’m bored”, “What’s near me at 4pm?” ➜ call your existing program recommendation endpoints and show suggestions.

Support navigator

“I’m stressed / need help” ➜ call crisis/wellness logic:

Show local resources (Kickstand, 211, crisis lines, etc.).

Use your existing CrisisDetectionModal.

Check-in buddy

Light encouragement after mood check-ins:

“I see you checked in as ‘drained’. That’s okay. Would you like to see some low-energy programs or talk to someone?”

Things to keep for later:

Deep resume-builder & career coaching.

Long-form journaling and AI reflections.

AI case management or clinical-style suggestions.

So Ximi still feels like a friendly, always-there companion, but your risk surface stays manageable.
