2) System Overview

High-level architecture diagram (described)
	•	Client: React + Vite SPA using React Router (src/main.tsx:10–42, src/router.tsx:1–159) with session-based auth via cookies and CSRF header injection (src/lib/api.ts:1–72, src/lib/session.tsx:1–122).
	•	PWA: vite-plugin-pwa Workbox runtime caching and offline support configured in vite.config.ts:24–71.
	•	Server: Express app in ESM (server/index.js:1–240) providing:
	•	Public routes: programs, events, crisis, transparency (server/index.js:172–179).
	•	Protected routes: checkins, profile, xid, ximi, etc, gated by CSRF, guardian verification, and rate limiting (server/index.js:184–211).
	•	Admin portal: separate route group with stricter rate limiting (server/index.js:163–165).
	•	Data: PostgreSQL via Drizzle schema (server/schema.ts) and session store connect-pg-simple created at boot (server/index.js:47–68).
	•	External dependencies: email provider, scheduler, push, maps, etc (startup checks in server/index.js:33–37, scheduler init via server/services/scheduler.js:1–44).

Service boundaries
	•	Single repo, single server process serving API plus static assets in production (server/index.js:216–279).
	•	No separate worker service, background jobs appear to run in-process (scheduler).

Data stores
	•	Postgres is primary store (Drizzle tables in server/schema.ts).
	•	Postgres session store table created on startup (server/index.js:59–67).

Critical user flows
	•	Youth onboarding and auth (register/login, session, CSRF token fetch).
	•	Daily check-in create and fetch (CSRF protected).
	•	Program discovery (public), saving programs (authenticated).
	•	Parent portal and consent flows (token based and/or parent auth routes).
	•	Admin portal login and management.

7) Security Review (OWASP-style)

Threat model summary

Attackers want:
	•	Unauthorized access to youth data, saved programs, check-in history, and any health profile info.
	•	Session hijacking or CSRF to perform actions as a logged-in user.
	•	Abuse admin portal.
	•	Exfiltration via offline caches on shared devices.

Likely entry points:
	•	Browser-based API calls via cookie sessions.
	•	Admin portal endpoints.
	•	PWA service worker cache.
	•	Public tokenized endpoints (consent, safety plan view links).

Vulnerability findings (P0–P3)

P0: PWA caches user-specific endpoints under /api/programs.*
	•	Evidence: Workbox runtime caching caches /\/api\/programs.*/ with StaleWhileRevalidate (vite.config.ts:35–47). The backend provides user-specific endpoints under that prefix, such as GET /saved/list (server/routes/programs.js:55–97).
	•	Risk: Sensitive or user-specific responses can be stored offline and potentially exposed on a shared device or across session changes. Also introduces correctness bugs where a user sees cached data after logout or after switching accounts.
	•	Concrete fix:
	•	Narrow the cache patterns to only truly public endpoints (example: /api/programs/public or /api/programs without /saved), or use NetworkOnly for any endpoint requiring session cookies.
	•	Add cacheWillUpdate to prevent caching when Set-Cookie is present or when response is user-specific.
	•	Acceptance criteria:
	•	Confirm via DevTools Application tab that requests to /api/programs/saved* and other authenticated endpoints are not stored in Cache Storage.
	•	Playwright test: login as user A, open saved list, logout, login as user B, confirm user A data is not shown offline.

P1: Admin portal password handling mismatch (hash vs plaintext)
	•	Evidence: .env.example says ADMIN_PASSWORD must be a bcrypt hash (.env.example:44–52), but login compares plaintext (server/routes/adminPortal.js:148–162) and imports bcrypt without using it (server/routes/adminPortal.js:31–41).
	•	Risk: Encourages insecure plaintext secrets and can prevent admin login if a bcrypt hash is configured.
	•	Concrete fix:
	•	Switch to bcrypt.compare(password, process.env.ADMIN_PASSWORD_HASH) and rename env var accordingly.
	•	Add rate limit and lockout messaging (adminLimiter already applied at mount, server/index.js:163–165).
	•	Acceptance criteria:
	•	With a bcrypt hash in env, login succeeds using the correct password and fails otherwise.
	•	Unit test covers success and failure cases.

P1: Raw error leakage in route handlers
	•	Evidence: Example route returns details: error.message on 500 (server/routes/events.js:227–230) instead of using the centralized production-safe handler (server/middleware/errorHandler.ts:36–55).
	•	Risk: Internal error details can leak schema info, query patterns, or stack context, useful for attackers and confusing for users.
	•	Concrete fix:
	•	Replace res.status(500).json({ ..., details: error.message }) with next(error) and let the error handler shape the response in production.
	•	Acceptance criteria:
	•	In production mode, API returns a generic message for 500s without exposing internal details.
	•	Logs still include full error context.

P1: ENCRYPTION_SECRET should be required in production at boot
	•	Evidence: Env schema marks ENCRYPTION_SECRET optional (server/config/env.ts:36–45), but encryption throws in production if missing (server/lib/encryption.ts:15–37).
	•	Risk: App can boot and then fail at runtime on first encryption action, causing outages and partial failures.
	•	Concrete fix:
	•	Enforce ENCRYPTION_SECRET required when NODE_ENV === 'production' at env parse time.
	•	Acceptance criteria:
	•	Server fails fast at startup with clear message when missing secret in prod.

P1: Missing validation on write endpoints (example programs create/update)
	•	Evidence: Program creation accepts raw body fields without schema validation (server/routes/programs.js:338–407).
	•	Risk: Data integrity issues, unexpected crashes, injection of bad values, poor UX due to inconsistent server acceptance.
	•	Concrete fix:
	•	Add zod schema for payloads and reject invalid data with 400.
	•	Acceptance criteria:
	•	Invalid payloads return structured 400s with error codes, valid payloads succeed, and tests cover both.

P2: CORS wildcard allowlist implementation may behave incorrectly
	•	Evidence: Wildcard conversion escapes dots after injecting a complex group, likely breaking the intended regex (server/middleware/cors.ts:20–40).
	•	Risk: Origins may be wrongly allowed or denied, leading to security exposure or production outages.
	•	Concrete fix:
	•	Use URL parsing plus a safe wildcard matcher (example: picomatch or micromatch), and compare normalized hostnames.
	•	Acceptance criteria:
	•	Tests show https://sub.roomxi.live is allowed when https://*.roomxi.live is configured, and disallowed for other domains.

13) Patch Suggestions (optional but preferred)

Patch 1 (P0): Stop caching user-specific /api/programs/saved*

Target: vite.config.ts:35–47
Approach: Replace broad regex with explicit patterns, and force NetworkOnly for authenticated endpoints.

// vite.config.ts (inside VitePWA workbox.runtimeCaching)
runtimeCaching: [
  // Public programs list only (example: /api/programs or /api/programs/public)
  {
    urlPattern: ({ url }) => url.pathname === '/api/programs',
    handler: 'StaleWhileRevalidate',
    options: { /* keep current options */ }
  },

  // Explicitly exclude saved and other user-specific endpoints
  {
    urlPattern: ({ url }) => url.pathname.startsWith('/api/programs/saved'),
    handler: 'NetworkOnly'
  },

Acceptance: Cache Storage does not contain any /api/programs/saved* entries after visiting those pages.

Patch 2 (P1): Admin portal password hash verification

Target: server/routes/adminPortal.js:148–162 and .env.example:44–52

// server/routes/adminPortal.js
router.post('/login', /* ... */, async (req, res) => {
  const { password } = req.body;

  const hash = process.env.ADMIN_PASSWORD; // rename to ADMIN_PASSWORD_HASH ideally
  if (!hash) return res.status(500).json({ error: 'Admin password not configured' });

  const ok = await bcrypt.compare(password, hash);
  if (!ok) return res.status(401).json({ error: 'Invalid admin password' });

  req.session.adminPortalAuthenticated = true;
  req.session.save(() => res.json({ success: true }));
});

Acceptance: bcrypt-hashed env works, plaintext env is not required.
