Production blockers (must fix before launch)

1) QR scanning will be blocked in production (camera disabled by headers)

File: vercel.json
You send:
	•	Permissions-Policy: camera=(), microphone=(), geolocation=()

But your app has QR scanning using camera:
	•	File: src/routes/QRScan.tsx (uses @zxing/browser / camera)

✅ Impact: QR scanning will fail for real users in production.
✅ Fix: Update Permissions-Policy to allow camera at least for self, e.g. camera=(self) (and geolocation if you use it).

⸻

2) Account deletion flow is broken (edge function requires confirmation; UI doesn’t send it)

Frontend: src/routes/Settings.tsx
Calls:
	•	supabase.functions.invoke('user-delete') with no body

Edge function: supabase/functions/user-delete/index.ts
Requires JSON body:
	•	confirm === 'DELETE_MY_ACCOUNT'

✅ Impact: Account deletion will error (likely 400/500 depending on body parsing).
✅ Fix: Send { confirm: "DELETE_MY_ACCOUNT" } from the UI (and handle errors cleanly).

⸻

3) Admin page is broken due to schema mismatch

File: src/routes/Admin.tsx
Checks:
	•	.select('role') and profile.role !== 'admin'

But schema defines profiles.is_admin boolean (no role column):
	•	File: supabase/schema.sql → public.profiles includes is_admin boolean not null default false

✅ Impact: Admin check will always fail (and the query can error because role doesn’t exist).
✅ Fix: Update Admin check to query is_admin and/or use your public.is_admin() helper.

⸻

4) Major privacy/security blocker: sensitive tables exist without RLS enabled

Your supabase/policies.sql enables RLS for some tables, but not all sensitive ones.

Tables present in schema (supabase/schema.sql) include:
	•	guardian_verifications (guardian contact details + tokens)
	•	health_profiles (medical info)
	•	consent_events (consent/audit-like history)
	•	breach_events (incident details)

But supabase/policies.sql only enables RLS for:
	•	programs, saved_programs, checkins, profiles, xids, attendance, consents, crisis_supports, admin_logs

✅ Impact: Depending on default Supabase grants, authenticated users may be able to read/write data they should never see (especially health_profiles and guardian verification records). This is a hard production blocker for a youth app.

✅ Fix: Enable RLS + add strict policies for:
	•	health_profiles → owner-only (and ideally conditioned on explicit health_data_consent)
	•	guardian_verifications → owner-only + staff/admin-only verification actions
	•	consent_events → owner-only insert/select (or admin-only select)
	•	breach_events → admin-only
