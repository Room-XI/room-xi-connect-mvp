1) What “Safety Plan” means in Room XI Connect

A personal, editable plan a youth can create and use when they feel overwhelmed, anxious, unsafe, or at risk.

It is not clinical, does not diagnose, and does not replace emergency services.

Core outcomes
	•	Youth can build a plan in 5 to 10 minutes.
	•	Youth can open it fast in a hard moment.
	•	Youth can optionally share read-only access with a trusted person.
	•	Youth can delete it any time.

Plan structure (MVP sections)

Keep it short, skimmable, and editable.
	1.	My early warning signs

	•	“What I notice in my body, thoughts, or behavior”

	2.	Things I can do right now

	•	3 to 10 coping actions (breathing, walk, music, shower, grounding)

	3.	Places that help

	•	“My room”, “outside”, “gym”, “community league”, etc.

	4.	People I can reach out to

	•	Trusted contacts with phone, relationship, and preferred method (call, text)

	5.	Professional support

	•	Pull from crisis_supports plus an “Add custom support” option

	6.	If things get worse

	•	Clear steps: “Text X”, “Call Y”, “Go to safe place”, “Call 911 if in danger”
	•	Always show the crisis sheet entry point

	7.	Notes for others

	•	“What helps me”, “What does not help me”, “How to support me”

Safety tone
	•	Calm, direct, dignity-first
	•	No blame language
	•	Always show: “If you are in immediate danger, call 911.”

3) Data model (Supabase)

Table: safety_plans (one plan per user, simple and clean)

Use a single row per user to keep it easy.

create table if not exists public.safety_plans (
  user_id uuid primary key references auth.users(id) on delete cascade,
  plan_version int not null default 1,
  data jsonb not null default '{}'::jsonb,
  last_reviewed_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index if not exists safety_plans_updated_idx
on public.safety_plans (updated_at desc);

data JSON shape (recommended)

{
  "warning_signs": ["..."],
  "coping_steps": ["..."],
  "safe_places": ["..."],
  "trusted_contacts": [
    {"name":"", "phone":"", "relationship":"", "preferred":"text|call"}
  ],
  "professional_support": [
    {"type":"crisis_supports", "id":"uuid"},
    {"type":"custom", "name":"", "phone":"", "notes":""}
  ],
  "escalation_steps": ["..."],
  "notes_for_others": {"helps":"", "not_helpful":"", "notes":""}
}

Table: safety_plan_shares (optional sharing)

This enables share links without weakening RLS.

create table if not exists public.safety_plan_shares (
  id uuid primary key default gen_random_uuid(),
  plan_user_id uuid not null references auth.users(id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  revoked_at timestamptz,
  label text,
  created_at timestamptz not null default now(),
  last_accessed_at timestamptz
);

create index if not exists safety_plan_shares_plan_idx
on public.safety_plan_shares (plan_user_id, created_at desc);

Optional audit: safety_plan_events

If you want stronger compliance and debugging.

4) RLS policies (Supabase)

In supabase/policies.sql add:

alter table public.safety_plans enable row level security;
alter table public.safety_plan_shares enable row level security;

create policy "Users can manage their own safety plan"
on public.safety_plans for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);

create policy "Users can manage their own safety plan shares"
on public.safety_plan_shares for all
using (auth.uid() = plan_user_id)
with check (auth.uid() = plan_user_id);

Important: do not allow public select on plans or shares. Sharing should happen via an Edge Function using the service role key.

5) Edge Functions (secure sharing)

You already use service role in supabase/functions/user-delete/index.ts. Use the same pattern.

Function A: safety-plan-share-create
	•	Auth required
	•	Generates a cryptographically strong random token
	•	Stores only a hash in DB
	•	Returns the raw token once

Function B: safety-plan-share-read
	•	No auth required
	•	Accepts token
	•	Hashes token, verifies not expired or revoked
	•	Returns read-only plan payload
	•	Updates last_accessed_at

Add these under:
	•	supabase/functions/safety-plan-share-create/index.ts
	•	supabase/functions/safety-plan-share-read/index.ts

Front end calls them using supabase.functions.invoke(...).

Non-negotiables for this feature:
	•	Default access is owner-only (RLS).
	•	Sharing is opt-in, revocable, and expires.
	•	Show “Delete plan” and “Delete account” linkage (your user-delete function already exists).
	•	Add a short on-screen note: “This plan is stored privately in your account. You can delete it any time.”

Optional but strong:

8) QA test plan (high priority cases)

Functional
	•	Create plan when none exists
	•	Edit each section, save, reload persists
	•	Create share link, open in private browser, plan loads read-only
	•	Revoke share link, link stops working
	•	Expired share link stops working

Safety and edge cases
	•	Plan loads even if crisis_supports table is empty, no crash
	•	Very long input is truncated or rejected gracefully
	•	Offline mode: show a clear warning if you do not support offline saves yet

Security
	•	Another authenticated user cannot read your plan (RLS check)
	•	Shared link reveals only the plan, not profile fields or user identifiers
	•	Token cannot be enumerated (long random token, hash stored)
