Room XI Connect – Full Code Review & QA Report

Overview and Key Features

Room XI Connect is a youth-focused web application built with React (TypeScript) and Vite, using Tailwind CSS for UI and Supabase for its backend (authentication, storage, PostgreSQL) ￼. The app’s goal is to help youth discover local programs, track their mood and attendance, manage consents, and provide admins with oversight tools. Major features and workflows include:
	•	Authentication & Onboarding: Users register with email/password, verify their email, and then complete a multi-step sign‑up form collecting personal details (name, age, location, etc.) and guardian contact if under 18. The app records consent to terms and privacy policies during signup ￼. (In production, email confirmation should be enabled – the onboarding flow must account for unverified users before profile completion.)
	•	Program Discovery: An Explore page lists programs with search filters, a map view, and the ability to save or unsave programs. Each program has a detail page showing its description and other info. Users can bookmark programs they’re interested in ￼.
	•	Mood Check-Ins (Home): On the Home page, users can log a daily mood check-in by selecting a mood level (1–6), tagging feelings, and leaving notes. The app displays the user’s current streak of daily check-ins and suggests programs based on their interests ￼.
	•	Safety Profile & Consents: A Safety Profile section allows users to provide emergency contacts, health info, and optional self-identification (e.g. Indigenous identity). Users can also manage fine-grained consents (e.g. photo consent, data sharing), which are recorded as consent events in the database for audit purposes ￼.
	•	Attendance Tracking (XID System): Each user is assigned an XID (an anonymized hashed ID). Users check in to in-person events by scanning a QR code or entering a code, logging their attendance. These attendance records can be captured offline and synced later via an encrypted queue ￼.
	•	Admin Dashboard: An Admin panel is available to authorized staff. It shows high-level stats (total users, check-ins, programs, attendance) and recent system audit logs (e.g. changes to important tables) ￼. Admins can monitor data and export logs (CSV/Excel export is planned but not yet implemented).
	•	User Settings: A Settings page allows users to sign out, delete their account, toggle notification preferences (currently local state only), see a placeholder for dark mode, and get instructions on installing the app as a PWA ￼.
	•	Offline Support: The app supports offline usage. A service worker (public/sw.js) caches static assets for offline access, and certain actions (like saving a program or recording attendance) are added to a local offline queue. The queue encrypts data (using AES-GCM) and retries syncing to Supabase when connectivity is restored ￼.

Code Structure & Quality: The codebase is organized clearly into dedicated folders for different concerns ￼. For example, all page components are under src/routes (e.g. Explore.tsx, Home.tsx, ProgramDetail.tsx, etc.), shared UI components in src/ui/, utility modules in src/lib/, and Supabase-specific scripts (SQL schema, Row Level Security policies, Edge Functions) in the supabase/ directory ￼. This modular structure makes the project easy to navigate. The React code uses functional components with hooks (for state and effects) and React Router for navigation. Overall code clarity is good – naming conventions are consistent and comments are used to explain complex logic (for example, the encryption routines and offline queue have comments referencing security/privacy considerations). The TypeScript types cover most data structures (like profile, program, log interfaces), although a few areas use any types or loose typing (e.g. the audit log JSON fields), which could be tightened for better type safety.

From an architecture perspective, the app’s design cleanly separates front-end concerns (views, state management) from backend logic handled by Supabase. The presence of comprehensive seed data and a deployment guide indicates forethought about ease of setup and testing. In general, the code is maintainable and follows modern React best practices. There are, however, some issues and inconsistencies that need to be addressed before the app is pilot-ready, as detailed below.

Supabase Integration and Configuration

The integration with Supabase is a core strength of the app. The database schema (see supabase/schema.sql) defines tables for programs, saved programs, check-ins, profiles, xids (user attendance IDs), consent events, and an admin log, among others. Row Level Security (RLS) is enabled on all user data tables, with policies that ensure users can only access their own records and that admin-only data (like admin_logs) is restricted to admins. A helper Postgres function is_admin() is defined to facilitate admin permission checks in these policies. This adds an extra layer of security by having the database enforce access rules in addition to the app logic.

Two Supabase Edge Functions are included: xid-create and user-delete. The xid-create function generates a new hashed XID for a user (used when a user attends an event for the first time or needs a new code). It uses a server-side secret (XID_HASH_SECRET) to salt and hash the ID. The user-delete function deletes a user’s account and associated data. It is invoked from the Settings page when a user chooses to delete their account, and it utilizes Supabase’s service role key to remove the user’s auth record and clean up related rows (ensuring a GDPR-compliant complete deletion). Both functions require certain environment variables to be set (the Supabase URL, anon key, service role key, etc.) so they can authenticate and perform their tasks ￼.

Environment variables are used for configuration. In development, these would be in a .env file; in production (e.g. on Vercel) they must be set in the deployment environment. Key variables include the Supabase project URL and anon key (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY), an encryption key for the offline queue (CRYPTO_KEY), and the secret keys for the edge functions (e.g. SUPABASE_SERVICE_ROLE_KEY, XID_HASH_SECRET) ￼ ￼. The app also defines feature-flag style env variables (such as VITE_ENABLE_OFFLINE_MODE, VITE_ENABLE_PWA, VITE_ENABLE_NOTIFICATIONS, VITE_ENABLE_XIMI_AI) which could be used to toggle features; currently these are all true by default, and the code does not heavily conditionalize behavior based on them – an area for potential future extension if a scaled-down mode or gradual rollout of features is desired.

One notable aspect is the offline queue encryption: the src/lib/queue.ts module encrypts queued data using the Web Crypto API (AES-GCM). A device-specific key is generated and stored in IndexedDB. It’s crucial that a CRYPTO_KEY (or some cryptographic secret) is configured in production so that encryption is performed properly – otherwise the queue might fail to encrypt/decrypt items, impairing offline functionality ￼. In the current code, the encryption appears to rely on the device-generated key alone (there is a mention of a CRYPTO_KEY in documentation but not directly in use in code), so ensuring the encryption logic is thoroughly tested (with real keys and various offline/online scenarios) is important.

Critical Code Issues Identified

Through reviewing the codebase, several critical issues have been identified. These issues are likely to cause runtime errors or broken functionality and should be addressed immediately:
	1.	Admin Panel Access & Logs – Broken Queries: The admin dashboard is not functional in the current code. The check for admin privileges is implemented by querying the profiles table for a role column ￼, but no such column exists in the schema (the schema uses an is_admin boolean flag instead). This means the admin check will always fail, and legitimate admins will be treated as regular users. Moreover, the dashboard attempts to load audit logs from a table named audit_logs ￼, which also does not exist (the actual table is admin_logs). As a result, the admin page will encounter errors or simply show no data. Suggested Fix: Use the existing is_admin field in profiles (or better, call a Supabase RPC like is_admin() to leverage RLS) to determine admin status, rather than a non-existent role. Also update the log query to fetch from admin_logs and adjust the code to the correct field names (old_record/new_record instead of old_values/new_values as used in the current UI) ￼. This will align the front-end with the actual database schema and allow the admin panel to function.
	2.	Attendance History & Count – Query Logic Bug: The functions getAttendanceHistory() and getAttendanceCount() in src/lib/attendance.ts are intended to retrieve a user’s past attendance records. However, both are written incorrectly: they call .in('xid_id', …) on the attendance table, passing a Supabase query object rather than an array of values ￼. This is a misuse of the Supabase API – .in() expects an array of IDs, but here it’s given a query (the result of selecting from the xids table). This will result in runtime errors or an empty result. Consequently, the app will not show any past attendance history or count, even for users who have attendance records. Suggested Fix: First query the xids table to get the list of XID UUIDs for the current user, then supply that list to .in('xid_id', [...]) when querying attendance ￼. The code should await the XID query and handle the case where no XID is found (e.g., a new user who hasn’t been assigned one yet) before proceeding to fetch attendance records.
	3.	Password Reset Page – Session Handling: The UpdatePassword.tsx component (used for handling password reset links) has a bug in how it checks for an active session. It calls supabase.auth.getSession() and immediately destructures the result assuming a synchronous response ￼. In reality, getSession() returns a promise, so the code is effectively running with session being undefined on first render. This triggers an immediate redirect to the login page, blocking legitimate use of the password reset form. Suggested Fix: Make the session retrieval asynchronous – for example, use an useEffect to call getSession().then(...) and only redirect if no session is found after the promise resolves ￼. This ensures that users who navigate via a valid password reset link can stay on the page to actually reset their password. Additionally, after a successful password update, the component uses a setTimeout to redirect after 3 seconds. This is mostly a UX concern (it could be confusing if the redirect happens too quickly/slowly); providing a direct “Go to Login” button or link in addition to the timed redirect could improve the experience ￼ (this is less critical than the initial redirect bug, but still worth refining).
	4.	Profile/Program Data Mismatch: There is a disconnect between the front-end and database for program details. The ProgramDetail.tsx component expects fields like long_description, contact_email, contact_phone, website_url, capacity, age_min, and age_max for each program ￼. These fields are not defined in the programs table schema (the schema has a simpler set of fields: title, description, tags, free flag, indoor/outdoor, cost, location, address, lat/lng, organizer, accessibility_notes, next_start, next_end) ￼. As a result, those extra fields will be undefined in the UI. This could lead to blank sections in the Program Detail page or runtime warnings. Suggested Fix: Align the UI with the database. If those additional fields are truly needed, they should be added to the database schema and populated (e.g., extend the programs table and update seed data accordingly). Otherwise, the front-end should be simplified to only display available data – for example, use the existing description field in place of long_description, remove or hide contact info fields if not provided by the backend, etc. ￼. This will prevent confusion and ensure users only see actual data.

(The above issue isn’t “critical” in the sense of crashing the app, but it is a significant functional inconsistency. Users will notice missing information on program pages, so it should be addressed for a polished pilot.)

In summary, the issues above (admin panel, attendance queries, password reset logic, and program field mismatches) are high-priority to fix. They affect core functionalities (admin oversight, attendance tracking, account recovery, and content display) and could impede the pilot usage of the app. Each of these should be verified after fixing (e.g., confirm that an admin can successfully view logs, that attendance history appears for a user with attendance records, etc.).

Other Issues and Recommendations

In addition to the critical bugs above, the review noted several other issues and potential improvements. While these may not block basic usage, addressing them will enhance the app’s completeness, usability, and readiness for broader deployment:
	1.	Dark Mode and Notification Features: The Settings page includes a Dark Mode toggle (currently labeled “coming soon”) and a Notifications toggle. At present, the dark mode is not implemented, and the notifications switch does not trigger any push notification setup – it only updates local state with no effect ￼. It’s recommended to implement these features or hide the toggles until they work. For Dark Mode, consider using Tailwind’s dark mode classes or a context to apply a dark theme across the app. For notifications, if the intent is to remind users to do daily check-ins, integrate with the Notifications API or a service worker to schedule a notification. (This might also involve asking for user permission and storing a preference, rather than just a local state toggle.)
	2.	Program Schema vs UI Mismatch: As mentioned, the program detail view expects fields that don’t exist in the database ￼. This should be resolved either by extending the schema or adjusting the UI. Currently, those undefined fields could confuse users or make the program pages look incomplete. Decide on a consistent set of program attributes for the pilot (perhaps simplifying to what is available: basic description, organizer, location details, etc.) and ensure both the front-end and backend use that same set of fields ￼. This will likely involve updating either ProgramDetail.tsx or the Supabase schema (and seeds) accordingly.
	3.	Admin Export and Filtering (Unimplemented Controls): The Admin panel UI shows a “Download” (export) button and a filter dropdown for logs, but these controls are not wired up to any functionality ￼. Clicking the export icon currently does nothing (no CSV or Excel is generated), and the filter dropdown does not actually filter the log list by table or date. This could be confusing to an admin user. If time allows, implementing at least basic versions of these features would be beneficial – for example, using a library like PapaParse on the client to export the loaded logs to CSV, or allowing the filter dropdown to client-side filter the logs by action type or table name. If implementation is deferred, consider hiding or disabling these UI elements during the pilot to avoid confusion.
	4.	Post-Password-Update UX: After a user successfully updates their password (via the reset link flow), the app shows a success message and then navigates back to the login screen after 3 seconds using setTimeout ￼. While this works, it could potentially race or feel abrupt across different browsers. It is recommended to test this flow on multiple devices. A more user-friendly approach might be to display a confirmation and include a “Back to Sign In” button, allowing the user to initiate the return to login immediately rather than waiting. This is a minor UX tweak, but it can make the experience smoother (especially if the timing or redirect behavior is inconsistent).
	5.	Offline Queue Reliability & Encryption: The offline queue system is an excellent feature, but it needs thorough testing. Ensure that the CRYPTO_KEY (encryption key) environment variable is set in production so that encryption works properly for queued data ￼. If the code is using a device-specific key only, make sure that scenario is handled (and that re-installing the app or clearing storage doesn’t orphan queued data that can no longer be decrypted). Test “network flapping” scenarios – e.g., record an attendance or check-in while offline, then reconnect and verify the data syncs correctly and is only entered once. Also test that if the user performs multiple offline actions, all of them eventually synchronize in order. The queue logic sets a short retry on regaining connectivity; verify that this doesn’t, for instance, cause a flood of rapid retries if the network connection is unstable. Robust error handling (with possible user feedback if something fails) would be ideal to add in the future for offline mode.
	6.	Edge Function Secrets & Security: Both the xid-create and user-delete edge functions rely on certain secrets being configured ￼. Before deployment, double-check that the Supabase project has the appropriate environment variables: SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, and XID_HASH_SECRET (with secure values). These should also be set in the hosting environment (e.g., Vercel) so that the front-end can invoke the functions properly. In terms of security, ensure that the edge functions themselves enforce authentication – for instance, the user-delete function should probably verify that the request is coming from an authenticated user and that the user making the request is indeed the one to be deleted (to prevent malicious deletion of another account). Typically, Supabase Functions include the JWT automatically; using that to validate the user context is important. Also, after account deletion, the client app should be prepared to handle the user being logged out or the JWT becoming invalid. (Logging the user out on the client after a successful deletion is a good practice to immediately end the session.)
	7.	Guardian Consent Verification Flow: For users under 18, the sign-up flow collects a guardian’s email or phone and is supposed to send a verification request. The current implementation always uses an email link method for guardian verification ￼. If a phone number is provided instead of an email, the system does not send an SMS – it still tries to treat it as an email. This is a limitation to be aware of. If supporting phone-based guardian verification is important, you would need to integrate an SMS sending mechanism (perhaps via a third-party API) or adjust the process. For the pilot, if email is the only method, consider explicitly asking for guardian email (to avoid users entering a phone expecting an SMS). Additionally, there doesn’t appear to be a completion step where the guardian’s response is processed – likely an area for future development (perhaps the guardian clicking an email link would mark a guardian_verifications entry as confirmed). Make sure to communicate to pilot users how this will work (or temporarily disable that requirement if it’s not fully implemented).
	8.	Data Export and Privacy Compliance: The Settings page has an Export Data option listed, but it’s just a placeholder (no actual data export functionality yet) ￼. For pilot, it’s okay that this isn’t implemented, but be mindful of privacy regulations like GDPR or Canada’s PHIPA if this app will handle personal data. Users may eventually request a copy of their data or the app should provide an export. Implementing a server-side function to gather all of a user’s data (profile, check-ins, attendance, consents, etc.) into a downloadable format (JSON or CSV files) is a recommended future enhancement. In the meantime, you may want to hide or clarify the “Export Data” item to avoid confusion during the pilot.
	9.	Accessibility (A11y) Considerations: As a youth-facing app, accessibility is important. A quick review of the UI components for semantic HTML and ARIA attributes is advised. For example, ensure form fields have labels, interactive elements (buttons, toggles) are reachable via keyboard, and modal dialogs (like the crisis support sheet or delete confirmation) trap focus when open and restore focus when closed. Color contrast should be checked – some text uses a “textSecondaryLight” style which might be low contrast against light backgrounds ￼. Test the app with a screen reader to see if all important information is conveyed. These adjustments will improve the experience for users with disabilities and demonstrate compliance with WCAG 2.1 AA standards. They may not all be fixed before a pilot, but identifying any major blockers (e.g., completely inaccessible features) is worthwhile.
	10.	Performance, Rate Limiting, and Security Enhancements: The app is small-scale, but as a best practice, consider adding rate limiting or other abuse prevention on key actions. For instance, since this is a youth app potentially open to the public, you might want to throttle how often a single IP can attempt logins or sign-ups to mitigate brute force attacks. Supabase doesn’t provide built-in rate limiting, but you could implement simple client-side checks or use a cloud function/proxy if needed. Also, verify that all Supabase RLS policies are properly in effect (it appears they are enabled and using the auth.uid() checks) ￼. In production, never disable RLS. Keep an eye on security configurations like Content Security Policy (CSP) and ensure all external resources (maps, if any, or analytics) are whitelisted properly. The provided CSP in index.html is fairly strict (self-only for most resources) – this is good for security. Just ensure it doesn’t break any needed functionality (e.g., if using Supabase, the connect-src in CSP should allow your Supabase endpoint and websocket) – adjust as necessary for any external APIs used.
	11.	Miscellaneous Observations: There are a few other minor points: The “About” page (src/routes/About.tsx) exists with information (presumably about the app or partners) but it’s not clear if it’s linked in the UI – you may want to add a link in settings or the home page if you want users to see it. Some configuration files (like tailwind.config.js, postcss.config.js) were duplicated in the archive listing but that’s likely just an packaging artifact – ensure there’s only one copy of each in the actual project to avoid confusion. The inclusion of CONTRIBUTING.md and replit.md in the repository is fine (for open-source or development context) but they have no effect on the running app. Finally, the AI helper “Ximi” (visible as the chat bubble on the Explore page via XimiDock.tsx) uses a heuristic approach for suggestions and crisis detection. It works entirely client-side with no external API calls, which is great for privacy – just be mindful of its limitations. Test that its keyword-based responses are appropriate, and consider toggling it off (VITE_ENABLE_XIMI_AI) if you find it giving inaccurate or unhelpful advice during the pilot.

Pilot Readiness Checklist

Before releasing Room XI Connect to pilot users, ensure the following setup and configuration tasks are completed:
	•	Database and Storage: Create a Supabase project and run all SQL migrations. Execute supabase/schema.sql to create tables and functions, then supabase/policies.sql to apply RLS policies ￼. Load initial data using the seed files (programs and crisis support contacts) so the app has content ￼. Also set up any storage buckets if the app uses Supabase Storage (not evident in code, but if needed for user profile images or similar, configure those with proper rules).
	•	Deploy Edge Functions: Using the Supabase CLI, deploy the two Edge Functions – xid-create and user-delete ￼. After deploying, configure the required environment variables for these functions in the Supabase dashboard (under Functions > Settings for each function). Specifically, set SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, and XID_HASH_SECRET to the appropriate values for your project (use strong random secrets for the hash secret and service role) ￼.
	•	Environment Variables: In the front-end hosting environment (e.g., Vercel), set up the environment variables as defined in the .env example. At minimum, define VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY so the app can communicate with your Supabase backend. Also set VITE_APP_NAME, VITE_APP_VERSION, etc., as needed (these might be used in the UI). If offline queue encryption requires a static key, set CRYPTO_KEY to a suitably random value ￼. (Even if not explicitly used in code, having it configured won’t hurt and may be used in future updates.) If you plan to integrate any third-party services (map APIs, SMS service for guardian alerts, etc.), configure those keys as well.
	•	Authentication Settings: In Supabase Authentication settings, enable email confirmations (so users must verify their email) and set up SMTP credentials for email sending (so that confirmation emails and password reset emails are delivered). Add your deployed app’s URL to the authorized redirect URLs (including paths like /auth/login and /auth/update-password). This ensures the magic links and reset links from Supabase will redirect back into the application correctly.
	•	Service Worker & PWA: Make sure the service worker (public/sw.js) is registered and functioning in the production build. Test that the app can be installed as a Progressive Web App (PWA) on mobile devices. The manifest.json and icons are present; verify they are correct for your app name. The service worker should be allowed (Service-Worker-Allowed: / header is set in vercel.json which is good) and should cache necessary assets. Check that after installation, the app works offline for basic browsing of cached pages.
	•	Content Security Policy: Review the Content Security Policy meta tag in index.html and adjust if necessary. Currently it’s strict (self and a few sources). If your Supabase endpoint is not covered by connect-src 'self' https:, you might need to add your Supabase URL. Ensure no console errors about CSP when the app tries to connect to Supabase or other services. Having a strong CSP (and other security headers like those set in vercel.json) is excellent for security – keep them in place for production.
	•	Admin User Setup: Before pilot, designate at least one user as an admin so that the Admin panel can be used. In the database, set profiles.is_admin = true for that user’s profile (or run an SQL update for that user’s ID). This will allow access to the Admin dashboard (after the code fix for admin access is deployed). Communicate to that admin how to use the dashboard and what to expect (and ensure they know it’s still a bit limited, e.g., export might not work yet).
	•	Testing in Staging: If possible, deploy the app to a staging environment first and run through all major user flows (see the test instructions below) before inviting real users. This will help catch any configuration or integration issues in an environment identical to production. In particular, test email delivery (confirmation and reset emails) using a real SMTP setup, and test the edge functions on the deployed Supabase (for account deletion and XID generation).
	•	Monitoring and Logs: Set up any monitoring for the pilot period. Supabase will log function calls and database errors – keep an eye on those logs for any errors (e.g., RLS denials, function exceptions). Also consider enabling Vercel/hosting logs and analytics to monitor usage. This will help quickly identify if any pilot user encounters a serious issue (so you can intervene or assist).

Recommended Testing Instructions

To validate the app’s functionality and ensure it’s ready for users, perform the following tests covering all major workflows. It’s ideal to test with both a user account under 18 (to exercise guardian flows) and an adult account, as well as with an admin account for the admin features.
	1.	User Registration & Email Verification: Create a new youth user account through the registration form. Use a test email that you can access. Verify that a confirmation email is sent by Supabase and that clicking the email link marks the email as confirmed in Supabase. Try the sign-up flow for both an under-18 user (enter a guardian’s email) and an 18+ user (no guardian info). Ensure that after submitting the registration, the app either logs the user in or prompts for email verification as expected. (If email confirmation is on, the user shouldn’t be able to proceed to fill profile info until confirmed – make sure the app’s flow accounts for this. If confirmation is off for testing, the user might go straight through.)
	2.	Onboarding Multi-Step Profile Completion: After registering (and confirming email if applicable), continue the onboarding process by filling out the profile steps. Enter data for name, age, location, etc., and submit each step. For an under-18 user, provide a guardian email or phone and observe that the app records a guardian verification request (you can check the guardian_verifications table in Supabase to see the entry). Ensure that consents (terms of service, privacy policy) are accepted and that a corresponding entry appears in the consent_events table (e.g., a “agreed” event for terms). Try to navigate back and forth in the multi-step form (if the UI allows) to see that data persists between steps or is properly validated. Finally, submit the profile; after completion, the user should land on the main app (Explore or Home page). Verify that a new record was created in the profiles table for the user.
	3.	Login & Logout Flow: Log out of the app (using the Settings -> Sign Out option), then attempt to log back in with the newly created account. Ensure that logging in takes the user to the appropriate home screen. Test that the login form prevents or shows errors for wrong credentials. Also test the “Forgot Password” link on the login page – it should navigate to the reset form. (Complete the reset process in a later step.) After logging in, also test the logout process again to confirm the session is properly cleared (the app should redirect to the login screen and not allow access to authenticated routes).
	4.	Program Exploration & Saving: Log in and navigate to the Explore page. Test the program listing and filtering functionality. If there are filters or search, try them out (e.g., filter by tags or search terms to see if the list updates). Toggle between list view and map view if both are available. Click on a program to view the Program Detail page. Verify that the program information is displayed correctly (title, description, location, etc.). Pay attention to those fields that were mismatched – confirm that no undefined or blank sections appear (after fixes, or if still blank, note it). On the detail page, try saving the program (there might be a “save” or bookmark icon). The UI should reflect the saved state (and an entry should appear in the saved_programs table for that user/program). Try unsaving it as well. Also test the saving feature directly from the Explore list if available (some UIs have a quick save button on cards). If possible, test the map: for example, click a program on the map and ensure it opens the detail or shows info.
	5.	Mood Check-In and Home Screen: Navigate to the Home page (or wherever the mood check-in interface is). Perform a mood check-in by selecting a mood value, choosing one or more feelings tags (if applicable), and entering a note. Submit the check-in. The app should record it and possibly update the UI to show the new entry (e.g., update today’s mood, increment streak count). Verify in Supabase that a new checkins record was created for the user. If the app displays a mood history or sparkline (there’s a Sparkline component for mood trends), check that it updates appropriately. If you have time, do check-ins on consecutive days (you can simulate this by manually adjusting the system date or just performing on actual separate days) to ensure the streak counter increases. Also test edge cases: e.g., try to submit the check-in form with no mood selected or no feelings – does the app prevent it or handle it gracefully? This is also a good time to test the notification toggle: flip the “Notifications” switch in Settings (it likely doesn’t do much yet, but ensure it doesn’t cause any errors). If feasible, simulate receiving a notification (this might not be possible without implementing it, but you can at least ensure the UI for notifications doesn’t break anything).
	6.	Attendance Check-In (QR & Manual): Test the in-person attendance flow. This might be split across the QRScan page and maybe the Program Detail (if “check in manually” exists). First, simulate scanning a QR code: if you have the ability to generate a QR code for an XID or program, do so (the format might be something like rx:program:<program_id> or similar – check qr.ts for format). Use the QRScan component – it should open your device camera. Scan the code and ensure the app recognizes it. It should then record an attendance entry linking your user (via their XID) to that program. If you can’t easily simulate a QR, use the manual check-in (if available): perhaps on a Program Detail there’s a “Check In” button that works without QR. Use that and confirm it records attendance. Key things to verify: the creation of an attendance record in the database (with correct program_id and your user’s xid_id), and that the app maybe shows a confirmation (e.g., “Checked in!”). If the app prevents duplicate check-ins or has a time window, test those rules too (e.g., try checking in twice for the same program). Also, test what happens if the user has no XID yet: the first time attendance for a new user should trigger the xid-create function. Ensure that works (a new XID should appear in xids table for the user, and then the attendance gets recorded referencing it). If possible, test an invalid scenario: scanning a QR for a program that doesn’t exist or is expired – the app should handle errors gracefully (likely by showing an error message).
	7.	Offline Functionality: This is a crucial test for the app’s resilience. Log in as a user and simulate going offline. For example, turn off your network connection or use your browser’s dev tools to simulate offline mode. While offline, attempt several actions: save or unsave a program, do a mood check-in, and (if possible) record an attendance (you might not be able to actually call camera for QR offline, but you could use a manual check-in if available). The app should not crash; ideally it should inform you that you’re offline and queue the actions. Perform a couple of these actions offline. Then restore connectivity. Within a short time (the app uses a small timeout), the queued actions should sync to Supabase. Verify that they indeed were transmitted: the previously saved program should now appear in your saved list (and in the DB), the offline mood check-in should be added to the checkins table and show up in the UI, and the attendance should be recorded. If the app provides any visual cue of syncing or error, note that. Also test refresh behavior: while offline, if you close and reopen the app (or refresh), does the app still have your queued actions in IndexedDB or are they lost? It’s good to know how robust the queue is. After connectivity returns and sync happens, ensure the app doesn’t duplicate entries (e.g., no double attendance or duplicate check-in). This offline test should be done on both desktop and a mobile device if possible, as behavior can differ.
	8.	Admin Dashboard & Restricted Access: Log in with an admin-designated account (after you’ve flagged one in the DB). Upon login, the app should identify the user as admin (after fixes, this should work via the is_admin field or RPC). Navigate to the Admin panel. Verify that it loads the statistics (user count, program count, etc.) – populate some dummy data if needed to see non-zero counts. Also verify that recent audit logs are listed. If no logs are showing, trigger some auditable events (for example, editing a program if that functionality exists, or having someone sign up which might log a profile creation). The admin_logs table in the DB records changes on certain tables – those should appear. Check that the log entries displayed match what’s in the DB. Try using the filter dropdown (if implemented by the time of test) to filter logs by action or table, and click the export button to see if a file downloads. Likely, these won’t work until implemented, but confirm that clicking them doesn’t break the page (and ideally, if they are non-functional, there should be no crash or a noop). Also test security: try accessing the admin URL with a non-admin account or when not logged in – the app should redirect or refuse access. Similarly, as an admin, ensure that restricted data (like other users’ profiles or consents) isn’t accessible outside the intended flows. For example, a normal user should not be able to query another user’s check-ins; this is mostly ensured by RLS, but worth a quick check if there’s any insecure client route.
	9.	Password Reset Flow: Test the password reset end-to-end. From the login screen, click “Forgot password” to go to the reset request page. Enter the email of an existing test user. The app/Supabase should send a password reset email. Check the email, click the reset link which should direct you to the UpdatePassword page in the app. Ensure the app does not immediately redirect away (after the fix, it should stay). Enter a new password and submit. Verify that you see a success message. You can either wait for the auto-redirect or use a provided button (depending on implementation) to return to login. Then try logging in with the new password to confirm it was actually changed. Also attempt an edge case: use an expired or already-used reset link (if you have one) to see if the app correctly handles the error (Supabase might show a message like link is invalid – ensure the app doesn’t just redirect blindly in that case). This will ensure the whole recovery process is solid.
	10.	Account Deletion: Finally, test deleting a user account. Log in as a regular user (not the admin, or you can test with both if desired). In Settings, use the Delete Account option. The app should probably ask for confirmation (if it shows a confirmation dialog, test that the dialog’s buttons work). Confirm deletion. The app will call the user-delete edge function – monitor the app behavior: it should either automatically log you out or at least show a success and then you should not be able to do anything as that user. Verify on the backend that the user’s row in auth.users and related data in profiles, checkins, etc. are removed. Attempt to log in again with the same credentials – it should fail (user no longer exists). Also check that any data that should be soft-deleted or anonymized is handled (for example, XIDs might be tombstoned via a tombstoned_at field instead of hard-deleted – ensure that was set if applicable). This test ensures the app meets data deletion requirements and doesn’t leave orphaned data.

By methodically running through all the steps above, you will verify that the application works as intended for end-users and that all major bugs have been squashed. Throughout testing, also keep an eye on the browser console and Supabase logs for any error messages or warnings – these can sometimes reveal minor issues (like React state updates on unmounted components, or CSP violations) that might not be immediately visible in the UI but are worth cleaning up. Addressing the critical bugs and the recommended improvements, and then passing these tests, will ensure Room XI Connect is robust and ready for its pilot launch.
